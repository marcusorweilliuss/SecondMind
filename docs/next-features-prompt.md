## Repo context you must reuse (do not reinvent)

- **Stack:** Next.js 14 App Router + TypeScript + Tailwind. Supabase (Postgres + Auth).
- **AI:** Groq via `src/lib/llm.ts` — `llmGenerate(system, user, opts)` and
  `llmJSON<T>(system, user, opts)`. Model is set by `GROQ_MODEL`
  (`llama-3.3-70b-versatile`, or `llama-3.1-8b-instant` for higher free limits).
- **Web search / citations:** `src/lib/tavily.ts` — `tavilySearch(query, opts)`.
  **All source links must come from Tavily results, never generated by the LLM.**
- **Auth in API routes:** `getUser(req)` from `src/lib/auth.ts` (accepts a Supabase
  cookie session OR a `Bearer` token from the Word/extension clients).
- **DB access in routes:** `createServiceSupabase()` from `src/lib/supabase/server.ts`
  (always scope every query with `.eq("user_id", user.id)`).
- **Existing API routes** (`src/app/api/...`): `factcheck`, `focus/check`,
  `autotable`, `signals`, `signals/list`, `notes`, `projects`, `task-context`,
  `radar/generate`, `radar/items`, `vectors`, `health`.
- **Shared UI:** `src/components/FactCheckPanel.tsx` (`FactResultCard`, `FactResult`),
  `src/components/PopOver.tsx` (centered animated modal).
- **Sentence locating / highlighting:** `src/lib/highlight.ts` —
  `locateClaim(text, quote)` (returns `{start,end}` or null; tolerant of reworded
  quotes, never returns a wrong-sentence match) and `chunkForWordSearch(segment)`
  (splits a sentence into Word-search-safe pieces).
- **Word client calls the same API** via the panel's local `authedFetch(path, init)`
  helper (adds Bearer + refreshes on 401). Word document reads use `readDocText()`;
  highlighting uses `Word.run` + `body.search(chunk, {matchCase:false, ignorePunct:true})`
  + `item.font.highlightColor`.
- **Tables in `supabase/schema.sql`:** `projects, signals, task_contexts,
  knowledge_notes, radar_items, interest_vectors, gmail_tokens`.

## Hard constraints (learned the hard way — respect all)

1. **On-demand only.** New heavy work (LLM + web search) runs on a **button**, never
   on the 30s / keystroke loops — Groq's free tier has low daily limits.
2. **Never 500.** Wrap every `llmJSON`/`llmGenerate` and `tavilySearch` call in
   try/catch and return a graceful `{...empty..., skipped:true, message}` with HTTP 200.
   Follow the exact pattern already in `src/app/api/focus/check/route.ts`.
3. **Real citations only.** URLs come from Tavily result objects. If you ask the LLM
   to pick a source, have it return the *index* of a provided result and map that
   index back to the real URL (see `factcheck` route's `source_number` handling).
4. **Highlighting must use `locateClaim` + `chunkForWordSearch`** — do not do naive
   `indexOf`. If a sentence can't be confidently located, skip its highlight (the
   finding still shows in the list).
5. **Mirror both surfaces** and keep the current vibe (dark, highlighter-yellow
   `accent`, rounded-full controls, casual lowercase copy, emoji). Reuse `FactResultCard`
   /`PopOver` where possible.
6. After each feature: run `npx tsc --noEmit` (do NOT run `npm run build` while a dev
   server is running — it corrupts `.next`). Then `git add -A`, commit with a clear
   message, and push.

## Build order & specs

### Step 1 — Claim strength + inline "needs source" / "overclaimed" flags
Extend the deep fact-check so each claim also gets a **support rating**, and add two
new inline flag types.

- In `src/app/api/factcheck/route.ts`, extend the verify step so each result adds:
  - `support`: `"well-supported" | "weak" | "unsupported"`
  - `flag`: `"needs_source" | "overclaimed" | null`
    - `needs_source`: a factual/statistical claim with no citation and no web
      corroboration found.
    - `overclaimed`: absolute/universal wording ("proves", "always", "everyone",
      "the first ever") that the evidence only partially supports.
  - Keep returning `quote`, `verdict`, `correction`, `explanation`, `source`.
- Extend `FactResult` in `FactCheckPanel.tsx` with `support` and `flag`; render a
  small colored chip for each. Add two verdict-highlight colors:
  `needs_source` → amber, `overclaimed` → orange/coral.
- Web (`focus/page.tsx`): fold the new flag categories into the existing highlight
  backdrop (`buildHighlightHtml`) using `locateClaim`.
- Word (`word/page.tsx`): fold into `highlightInWord` (new colors via `highlightColor`).
- **Acceptance:** writing "Studies prove coffee always cures headaches" surfaces an
  `overclaimed` flag + amber/orange highlight; a bare statistic with no support gets
  `needs_source`.

### Step 2 — Fact-check against stronger/authoritative sources
Improve source quality in `factcheck` (and reuse for Step 3).

- Add a helper in `src/lib/tavily.ts` (e.g. `tavilySearchAuthoritative(query)`) that
  runs the search and prefers reputable domains (gov/edu/org, major reference sites,
  established news, primary sources). Tavily supports `include_domains` — optionally
  do one pass restricted to a curated allowlist, then a general pass, and merge.
- Tag each returned source with a `credibility: "high" | "medium" | "unknown"` derived
  from the domain, and surface it on the source chip in `FactResultCard`.
- **Acceptance:** citations lean toward authoritative domains; each shows a credibility tag.

### Step 3 — Suggested reading (useful/interesting sources)
A new on-demand panel that recommends things to read for the current draft.

- New route `src/app/api/suggest-sources/route.ts`: takes `{ writing }`, uses the LLM
  to derive 3–5 reading angles (like `radar/generate`'s vector extraction), runs
  `tavilySearch` per angle, and has the LLM write a one-line "why this is worth reading"
  per result (index-mapped to real URLs). Return `{ suggestions: [{title, url, source,
  why, angle}] }`.
- UI: a **"📚 suggested reading"** button on both surfaces; render results as cards
  with a **"save to project →"** action that reuses `POST /api/signals`
  (so a suggestion becomes a saved signal — mirrors the Radar "save" behavior).
- **Acceptance:** clicking it returns real, relevant links with a reason each, savable to a project.

### Step 4 — Save your own writing as a signal
Let the writer file a selected passage of their *own* draft as a research signal.

- Web: add a "save selection as signal" affordance on the writing surface (use the
  textarea's `selectionStart/selectionEnd`; if nothing selected, use the whole draft).
- Word: the panel already has "save highlight"; make sure it tags self-authored content.
- Server: reuse `POST /api/signals`. Add an optional `origin: "self" | "web"` field to
  the `signals` table (migration in `supabase/schema.sql`: `alter table signals add
  column if not exists origin text default 'web';`). Set `origin:"self"`,
  `source_title:"My draft"` for self-authored. Skip the "connected_to" web-y framing
  for self signals (or label it "your own note").
- **Acceptance:** a highlighted passage of my own writing appears under the chosen
  project's signals, marked as self-authored.

### Step 5 — Auto-bibliography generation
Generate a formatted reference list from a project's cited sources.

- New route `src/app/api/bibliography/route.ts`: takes `{ project_id, style }`
  (`style` ∈ `apa | mla | chicago`, default `apa`). Gather sources: all `signals`
  with a `source_url` in that project + all `radar_items` saved to it. For metadata
  (title/site/date) use what's stored; optionally enrich a missing title via one
  `tavilySearch`. Ask the LLM to format them into the chosen citation style
  (return `{ style, entries: string[], formatted: string }`). Do **not** invent URLs
  or authors — only format what's provided; mark unknown fields as "n.d." etc.
- UI: a **"🔖 bibliography"** button. Web → modal with copy-to-clipboard + style picker.
  Word → insert the formatted list at the end of the document via `body.insertText`
  (or `insertParagraph`) under a "References" heading.
- **Acceptance:** a project with 3 saved sources yields a clean APA list; Word can
  insert it into the doc.

### Step 6 — "Can consider" analysis (supporting points / tensions / future work / open questions)
An on-demand structured critique of the draft.

- New route `src/app/api/consider/route.ts`: takes `{ writing }` (+ optionally the
  active `task_context` for framing). One `llmJSON` call returning:
  `{ supporting_points: string[], tensions: string[], future_work: string[],
  open_questions: string[] }`. Keep each list to ~2–4 concise items grounded in the
  actual text (no generic filler).
- UI: a **"🧩 things to consider"** button opening a panel/modal with four labeled
  sections (reuse `PopOver` on Word's narrow panel; a modal on web). Each item can be
  **inserted into the draft** as a comment/bullet (optional).
- **Acceptance:** returns draft-specific supporting points, tensions, future work, and
  open questions — not boilerplate.
